# Rust v2: runtime gap analysis

Source snapshot: branch `rust/v2`, HEAD `f35b15a90965748e62e841b671cbb99f56841185`, reviewed 2026-11-08. The worktree was clean before this report. References below are repository-relative `file:line` citations to this snapshot.

This is a source review, not runtime qualification. The binding contract is `docs/rust-v2/IMPLEMENTATION.md`, read in full; its work packages (WPs) are numbered 1–12 at lines 59–81. Later task/run numbers in progress notes are a different numbering system. Other Rust v2 documents were skimmed for context and the latest progress entries checked against code. Builds, tests, CLI execution, network traffic, container operations and VM experiments in this review: **NOT_RUN**. No protected deployment configuration, secret archives or production state was inspected. No Cargo target directory was created.

## Finding

**There is no shipped executable path that activates a Mullvad exit and serves real Tailscale clients.** This is more than an absent CLI verb, but less than an absent implementation: substantial native networking, nftables, confinement, monitoring and watchdog components exist. They are split between older lab-connected activation code and a newer secret-safe custody chain that stops before activation.

Three independent barriers establish this:

1. `vprouter` exposes only `validate`, `status`, `probe`, `migrate inspect|plan` and `diagnose`; it does not depend on the launch crate. Status/probe return `guard_runtime_unimplemented`, `actively_verified:false`, `activation_ready:false` and exit 2. Validation and diagnosis also hard-code false readiness. Migration plans are deliberately non-applicable (`crates/vprouter/src/main.rs:19`, `crates/vprouter/src/main.rs:47`, `crates/vprouter/src/main.rs:76`, `crates/vprouter/src/main.rs:80`, `crates/vprouter/src/main.rs:142`; `crates/vprouter/Cargo.toml:8`).
2. The other host entry point cannot admit a launch: `StagingEvidence::parse` unconditionally returns `LaunchUnavailable` after decoding/checking artifact kind; `Admission::launch` independently returns the same error (`crates/vprouter-launch/src/spec.rs:132`; `crates/vprouter-launch/src/lib.rs:132`). The comment claiming no worker implementation exists is stale in light of the enrolled monitor described below; the actual refusal remains effective.
3. The newer secret-safe bootstrap yields an opaque `BootstrappedOwner`. Its only implementation is `Drop`; there is no consumer that turns it into usable links, daemon placement or a monitored exit (`crates/vprouter-launch/src/attachment/operational/bootstrap.rs:277`, `crates/vprouter-launch/src/attachment/operational/bootstrap.rs:566`, `crates/vprouter-launch/src/attachment/operational/bootstrap.rs:603`). Searches for all references find construction, drop, a size test and lab use, not an activation continuation. Its own lab witness explicitly reports placement, UP and health readiness unauthorized (`crates/vprouter-launch/src/attachment/operational/bootstrap.rs:1253`).

These refusals should remain until reviewed activation prerequisites exist. Replacing either error with `Ok(())` would not create a safe runtime.

## 2. Required one-exit data path and current wiring

Required packet path once authorized:

```text
protected Linux client application
  -> client guard -> client tailscaled -> encrypted Tailscale transport
  -> exit tailscaled in DATA namespace -> tailscale0 (decrypted client IPv4)
  -> DATA forward policy + CGNAT-source SNAT -> WireGuard interface
  -> WG's retained birth-namespace UDP socket in TRANSPORT namespace
  -> transport veth -> host scoped policy/NAT -> WAN -> configured Mullvad endpoint
```

The exit's Tailscale control/relay and provider-check traffic must also leave through WireGuard. The only host–transport veth is outside DATA; DATA must never acquire a plaintext host-WAN route. Return traffic follows conntrack and the reverse tunnel path. Independent host/terminal authorities must close this path without relying on a functioning worker or tailscaled. Client-side denial is separately necessary when an exit disappears.

Labels below refer to reachability from a deployable owner, not merely a function calling another function. **exists+wired** means usable through a current product path; **exists-but-unwired** includes working private/lab chains that no product runtime constructs; **missing** means no actuator/continuation for that obligation was found. No traffic-serving step qualifies as exists+wired end-to-end in this snapshot.

| 12. Stop/restart/rearm/reconcile without losing identity or quarantine | **exists-but-unwired** components; product lifecycle **missing** | Journals/retention/owner scheduling exist. Worker explicitly refuses to silently reopen full Offline; fresh host-authorized lifecycle is required. CLI has no start/stop/exit mutations or native restart recovery driver (`crates/vprouter-worker/src/engine.rs:583`; `crates/vprouter-launch/src/owner.rs:2560`; `crates/vprouter/src/main.rs:19`). |
| 13. Client remains protected if exit disappears, selection changes, DNS/proxy routes drift | **missing** runtime | Core guard model and offline nft rendering only; no native persistent client installer/daemon or SOCKS/HTTP runtime (`crates/vprouter-core/src/client.rs:259`, `crates/vprouter-core/src/client.rs:439`; `crates/vprouter-netfilter/src/client.rs:26`). Exit containment alone cannot establish client no-fallback behavior. |

### Why the two setup generations cannot simply be joined by calling the old function

`GuardTransport::activate` is substantial: it takes a parsed private `Profile`, quarantines, creates WG in TRANSPORT, moves it into DATA, journals link indices, activates routes/links under quarantine and enters Bootstrap (`crates/vprouter-launch/src/transport.rs:682`). Its callers are exclusively in `transport_lab.rs` (`crates/vprouter-launch/src/transport_lab.rs:1410`, `crates/vprouter-launch/src/transport_lab.rs:1731`).

The newer path assumes the parent **never ingests private material** before forking native roles: it pins profile descriptors and confines profile validation/provisioning (`crates/vprouter-launch/src/secret.rs:90`; `crates/vprouter-launch/src/attachment/provision.rs:621`). Parsing a profile or raw WG GetDevice reply permanently marks process secret ingress; even discarded private-key attributes count (`crates/vprouter-core/src/profile.rs:133`; `crates/vprouter-core/src/secret_boundary.rs:1`; `crates/vprouter-network/src/native.rs:402`). Native-role preflight/child setup reject that parent (`crates/vprouter-native-role/src/linux.rs:38`, `crates/vprouter-native-role/src/linux.rs:220`).

Thus calling today's `load_configuration` in a future fork-capable host runtime, then calling the new child pipeline, is invalid: that loader reads/parses profiles (`crates/vprouter-linux/src/lib.rs:54`). Nor can a public profile be fabricated into the old native authority. The required bridge must consume retained, constructor-origin ownership/receipts, use public projections for planning, and keep privileged secret operations in confined children. `OperationalOwner` expressly grants no UP, placement, permits or READY on its own (`crates/vprouter-launch/src/attachment/operational.rs:1`). This custody-preserving continuation is a primary engineering milestone.

Atomic nft operations are scoped to one namespace. There is no single atomic transaction spanning host, TRANSPORT and DATA. Cross-scope safety depends on quarantine, sequencing, readback, independent containment and retention on ambiguity; preserve those properties when connecting the components (`crates/vprouter-netfilter/src/enforcement.rs:125`, `crates/vprouter-netfilter/src/enforcement.rs:145`).

## 3. Minimal ordered milestones to one real lab exit

Target: **one independently enrolled disposable Mullvad exit in an isolated local VM, with a real protected Linux Tailscale client and independent external packet observation, ready for substantive leak/fault testing**. This is not primary-identity migration, release acceptance, five exits or cross-platform completion. “External” means outside the processes/namespaces under test; it need not mean a remote installation. All eventual experiments remain local per `docs/rust-v2/IMPLEMENTATION.md:109`.

Estimates are engineering judgments, not measured throughput: S = a small local change, roughly 1–3 focused engineer-days; M = moderate integration, roughly 3–8; L = coupled lifecycle/security integration, roughly 7–15. Ranges overlap because integration risk affects size. They include focused tests and review, assuming existing components can be retained. They exclude unavailable hardware/account provisioning delays. Likely files name scope, not authorization to modify them in this research task.

### L1 — Establish a reviewable, refusing-by-default lab runtime contract (S, 1–3 days)

- **Scope:** Select one supported x86_64/systemd/cgroup-v2/Docker lab platform. Define the independent host owner entry point, pinned program/image staging producer, public configuration input, authored host/WAN baseline, resource ownership and phase gates. Admit only the reviewed local lab fixture after prerequisite checks. Define sanitized status fields and explicit unverified reasons. Do not simply remove current public refusals or repurpose test markers as runtime authority.
- **Likely files:** `crates/vprouter/src/main.rs`, `crates/vprouter-launch/src/{lib,spec,programs,process,supervision}.rs`, `crates/vprouter-linux/src/lib.rs`; lab staging/manifest tooling and focused docs.
- **Acceptance:** Supported fixture admitted by exact program/image/configuration/namespace/cgroup binding; altered hash, wrong owner, stale generation, foreign namespace and unsupported platform refuse without opening traffic. Ordinary product invocation remains refusing until its runtime gate is met. Parent remains single-threaded and pristine; no secrets in argv/output.
- **Risks:** Immutable image/program hash contracts, host baseline policy and OCI assumptions may require coordinated artifact changes. Service manager provenance must be real, not asserted by JSON.

### L2 — Construct and retain the complete quarantined resource owner (M, 4–7 days)

- **Scope:** Add a bounded native Docker lifecycle executor or an explicitly specified, independently verified pre-staged lab container contract. The latter is the minimum initial fixture path; it must not be represented as WP5 lifecycle completion. Construct one inert gateway, owned DATA/TRANSPORT namespaces, allocation/journal lock, producer group and the newer secret-validation/provision/move/attachment/host-addition/bootstrap chain. Poll and retain all failure owners/children. No link activation or arbitrary cleanup authority from a completion ACK.
- **Likely files:** `crates/vprouter-linux/src/docker.rs` if lifecycle is included; `crates/vprouter-launch/src/{secret,owned,owner,attachment,producer}.rs`, `crates/vprouter-launch/src/attachment/`, `crates/vprouter-native-role/src/`; lab fixture provisioning.
- **Acceptance:** Real pinned container/PID/root/cgroup/ns admitted; wrong root/PID, descriptor substitution, profile replacement, duplicate ownership and crash at each setup boundary fail under quarantine. Prove WG birth in TRANSPORT and move to DATA; no plaintext veth in DATA. Capture starts before any possible protected traffic. Private key never reaches parent. Only one enabled exit creates runtime resources.
- **Risks:** Existing fixture machinery performs some staging outside the Rust runtime; ownership must be explicit. Cleanup/reaping is not authority to delete or reuse resources. Shared-host baseline must not learn drift as trusted state.

### L3 — Add the typed bootstrap-to-activation bridge and forwarding admission (L, 7–11 days)

- **Scope:** Consume `BootstrappedOwner` into a retained activation authority without reconstructing authority from public metadata. Bind actual link indices and exact namespace identities durably. Reuse/refactor audited link/routes/UP primitives into suitable confined public-only operations. Add explicit host/DATA IPv4 forwarding admission/setup/readback, with declared ownership/restoration for any shared host sysctl. Preserve IPv6 denial and producer-only Bootstrap; reconcile ordering because the new path already reaches Bootstrap while old activation expects full Offline.
- **Likely files:** `crates/vprouter-launch/src/attachment/operational/{bootstrap.rs,<new continuation>}`, `crates/vprouter-launch/src/{transport,kernel,owned}.rs`, `crates/vprouter-network/src/{guarded,native,plan}.rs`, `crates/vprouter-native-role/src/`, `crates/vprouter-netfilter/src/enforcement.rs` only if the existing API needs safe adaptation.
- **Acceptance:** Real host–TRANSPORT endpoint path and WG DATA default work while client forwarding remains blocked. Verify required forwarding values in the correct namespaces, IPv6 denial, no extra DATA default/interface, exact endpoint/peer/key and no parent secret ingress. Inject failure before/after every UP, route and sysctl operation; retain quarantine and ownership. Test foreign host traffic remains unaffected.
- **Risks:** This is the main missing typed connection. Existing native methods may use raw WG queries that taint the parent. Shared sysctls, routes and nft hooks cannot be changed casually. Working component code may need relocation rather than a thin wrapper.

### L4 — Bring up one independently enrolled tailscaled under the retained owner (M, 4–6 days)

- **Scope:** Provision a distinct disposable test enrollment/state through a controlled workflow; bind node ID/IP, authorized routes, exact peer roster, allocation and pinned bundle in the enrollment document. Launch fixed tailscaled inside DATA with private mount/state/cgroup/TUN restrictions. Keep advertisement withdrawn until healthy approval. Connect the new activation owner to daemon handoff; preserve identity on stop/restart.
- **Likely files:** `crates/vprouter-launch/src/{enrollment,daemon,actual,handoff,programs,kernel}.rs`, `crates/vprouter-worker/src/{bootstrap,localapi,operation}.rs`; protected lab enrollment authoring tooling.
- **Acceptance:** Real control-plane registration/approval and stable node identity through Mullvad, with no host DNS/default escape; daemon has only intended NET_ADMIN and monitor no capabilities. Startup can reach Tailscale control/relay under producer-only Bootstrap, without client forwarding. Wrong/expired node, extra peer, unsafe preferences, missing approval or substituted enrollment stay offline. No identity cloning or enrollment reset on restart.
- **Risks:** Enrollment validation is already strict but no integrated enrollment workflow exists. Exact peer-roster matching means adding a legitimate test client needs an authorized new roster, not a weakened comparison. Tailscale's actual routes/TUN/netlink behavior must fit current audited structure.

### L5 — Bind live monitoring, policy publication, watchdog and terminal stop (L, 7–11 days)

- **Scope:** Construct enrolled monitor, guard structural channel, protected health publisher and independent per-scope expiry writers from the same lifecycle. Start and verify terminal containment before any Ready transition. Wire authenticated Structure/Heartbeat/Prepare/Persist/Commit to native policy/identity evidence. Expose fresh observational status. On sample failure, withdraw/quarantine and stop; rearm requires a new host-authorized lifecycle, not automatic Bootstrap reopening.
- **Likely files:** `crates/vprouter-launch/src/{handoff,expiry,publisher,owner,transport}.rs`, new activation continuation; `crates/vprouter-worker/src/{engine,monitor,operation,localapi}.rs`, `crates/vprouter-linux/src/status.rs`.
- **Acceptance:** Real 5s provider sampling, exact positive Mullvad server/public egress, handshake <180s, heartbeat <45s, independent 90s watchdog; eligible retry only once after 1s with fresh structural evidence. Multiple recovery samples and actual route approval precede client Ready. Stale/replayed publication, worker death, frozen guard, killed owner, failed fsync and failed policy commit quarantine without relying on the failed component. Fence delayed stale writers. Late containment stays FAIL, not timely PASS.
- **Risks:** Timing and fsync/audit cost are real; strict freshness cannot be relaxed to pass slow emulation. A functioning monitor alone is not proof of independent guard containment. Existing failure-stop semantics must be reflected honestly in lifecycle/status.

### L6 — Connect a protected real client and independent leak monitor (M, 3–7 days)

- **Scope:** Use one disposable local Linux Tailscale client with a minimal real kernel guard sufficient for the test workload, including IPv4/DNS/IPv6 and narrowly identified daemon transport exemption. Keep this explicitly short of complete WP8 proxy/install support. Add capture/marker orchestration outside the runtime: client WAN, host WAN, TRANSPORT and DATA, plus successful application egress observation. Publish exact artifact/configuration bindings and capture loss/unknowns.
- **Likely files:** lab client/capture harnesses; a bounded native client actuator using `crates/vprouter-core/src/client.rs` and `crates/vprouter-netfilter/src/client.rs`, or independently established equivalent test-client enforcement; acceptance evidence tooling/docs.
- **Acceptance:** Positive controls show each observation point detects the forbidden markers it is supposed to detect. Real client TCP/UDP/IPv4/DNS reach the expected Mullvad exit; IPv6 does not escape. WireGuard-down, exit disappearance and worker/guard kill produce no client WAN fallback or plaintext host/TRANSPORT leakage. Lossy/missing capture is unverified. Start capture before the tested startup/boot. Include client route/exit selection in evidence. The outside monitor must be able to distinguish encrypted Tailscale/WG transport from forbidden application traffic.
- **Risks:** Exit failure can trigger client-local fallback independently of the server. A provider JSON response, HTTP success, synthetic packet model or zero packets with no positive control is insufficient. Packet capture bootstrap and control traffic classification often reveal additional policy work.

After L1–L6, the result is **testable single-exit lab integration**, with initial smoke/failure evidence, not a completed leak/fault qualification. L2 can initially rely on a tightly admitted pre-staged fixture; native creation/update/deletion remains a later explicit obligation. Budget roughly **25–45 focused engineer-days (5–9 engineer-weeks)** for this target, allowing overlap between shared milestone code and review. This estimate assumes the missing bridge can reuse current ownership/confinement mechanics; it is not a promise that tests will reveal no redesign.

## 5. Runtime hazards that must remain removed, unreachable or explicitly gated

This review did not demonstrate a deployed fail-open exploit. Most public paths refuse precisely because integration is incomplete. The following are concrete exposure hazards when building the runtime:

1. **Secret-tainted owner reuse.** The CLI configuration loader reads private profiles; raw native WG observation also marks ingress. Reusing those in the fork-capable runtime parent defeats the new boundary or causes confinement refusal. Keep secret reads in admitted children and carry only constructor-origin public evidence/custody. Do not reset the ingress marker or weaken child preflight (`crates/vprouter-linux/src/lib.rs:54`; `crates/vprouter-network/src/native.rs:402`; `crates/vprouter-core/src/secret_boundary.rs:1`; `crates/vprouter-native-role/src/linux.rs:38`).
2. **Granting readiness from a low-level method or ACK.** `Enforcement::ready` enforces scoped policy, but its API explicitly leaves health/advertisement decisions to the guard. It does not independently prove provider health or Tailscale authorization. The private older `Control` notification channel explicitly says ACK means recorded only. Keep that draft path unreachable as readiness authority and use the newer operational publication/native proof path (`crates/vprouter-netfilter/src/enforcement.rs:142`; `crates/vprouter-worker/src/engine.rs:226`; `crates/vprouter-launch/src/handoff.rs:1173`).
3. **Turning lab descriptors/selectors into product authority.** Prepared fixture profiles, synthetic peers/endpoints, `--ignored`, exact lab WANs and root-owned lab markers are component test inputs, not proof of actual enrollment/provider/client coverage. Ship product targets without lab modes or a general “skip checks” option. Do not infer runtime completion from `actual_lab` or `operational-profile` names (`crates/vprouter-launch/Cargo.toml:28`; `crates/vprouter-launch/src/lib.rs:6`; `crates/vprouter-launch/src/actual_lab_main.rs:324`; `crates/vprouter-worker/src/lab_main.rs:21`; `crates/vprouter-launch/src/transport_lab.rs:1051`).
4. **Permits before independent expiry custody.** Bootstrap can carry producer traffic and Ready allows application forwarding. Runtime startup must verify all terminal writers/guard bindings before either transition that depends on them. A worker's successful request or heartbeat cannot stand in for an independent expiry executor. Do not reinterpret `LateVerified` as on-time containment (`crates/vprouter-netfilter/src/enforcement.rs:125`; `crates/vprouter-launch/src/handoff.rs:585`; `crates/vprouter-launch/src/expiry.rs:754`).
5. **Unowned forwarding changes or a blanket firewall repair.** IPv4 forwarding must be explicit, but setting a shared host sysctl can affect unrelated traffic; require preflight, declared ownership and restoration policy. Preserve scoped host drops, quarantine before route/UP changes, generation checks and unrelated policy. Do not “repair” drift by accepting the new host snapshot or globally flushing nftables (`crates/vprouter-netfilter/src/policy.rs:223`; `crates/vprouter-network/src/guarded.rs:1268`; `crates/vprouter-network/src/guarded.rs:1368`; `crates/vprouter-launch/src/attachment/host_addition.rs:145`).
6. **Silent recovery or identity/peer relearning.** Full Offline deliberately stops health traffic and requires a fresh host lifecycle. Do not periodically reopen Bootstrap on a timer. LocalAPI checks exact enrolled identity/peer roster; adding legitimate peers requires authorized roster transition, not learning whatever peers happen to be present (`crates/vprouter-worker/src/engine.rs:583`; `crates/vprouter-worker/src/localapi.rs:276`; `crates/vprouter-worker/src/localapi.rs:382`).
7. **Treating retained ownership as a cleanup leak to fix automatically.** New owner Drop retains native custody and failure contexts intentionally. Reaped helpers, elapsed time or a lost owner are not proof that deleting namespaces/tables/state is safe. Ambiguous recovery keeps quarantine and refuses resource reuse (`crates/vprouter-launch/src/attachment/operational/bootstrap.rs:588`; `crates/vprouter-launch/src/attachment/operational.rs:196`; `docs/rust-v2/IMPLEMENTATION.md:22`). Bound retained work and provide explicit reconciliation rather than dropping locks or deleting by name.
8. **Unsupported confinement/manager bypass.** Current setup expects initial user namespace/root, supported seccomp/LSM state, a specific Docker systemd cgroup path, and systemd owner verification. Allowing arbitrary cgroup paths, privileged containers, host networking or persistent SYS_ADMIN to make another host “work” would discard the inspected security contract. Add native supported variants and tests; otherwise refuse (`crates/vprouter-launch/src/process.rs:250`, `crates/vprouter-launch/src/process.rs:283`; `crates/vprouter-launch/src/supervision.rs:303`; `docs/rust-v2/IMPLEMENTATION.md:17`).
9. **Server-only no-fallback claims.** Server quarantine cannot prevent an unguarded client selecting its WAN when the exit disappears. Client DNS/IPv6/proxy protection needs an actual runtime. Direct must stay explicitly selected and labeled exposed; current direct rejection is protective (`crates/vprouter-netfilter/src/client.rs:1`; `crates/vprouter-core/src/client.rs:439`; `crates/vprouter-worker/src/engine.rs:120`).
10. **Promoting metadata or drafts into live proof.** Cached status, fixture migration receipts, release declarations and offline performance validators cannot authorize traffic or publication. Preserve `not_tested`/NOT_RUN and refusing service drafts until actual executors and evidence replace them. Worker health snapshots themselves still label DNS/IPv6 NotTested; Ready is not an independent DNS/IPv6 capture certificate (`crates/vprouter-linux/src/status.rs:133`; `crates/vprouter-worker/src/engine.rs:205`; `crates/vprouter-core/src/migration/contract.rs:76`; `tools/release_engineering/release.py:778`).

## 6. Remaining effort and decision

The project has invested heavily in **mechanically constrained native components and evidence custody**, while the integrated product lifecycle remains absent. It is inaccurate to call it only stubs, and equally inaccurate to describe the remaining work as adding `start` to Clap. The highest-risk gap is consuming the new pristine-parent bootstrap authority into actual activation and the older operational daemon/monitor/watchdog chain without losing ownership, freshness or confinement guarantees.

Planning estimate for one experienced engineer familiar with this tree, with supported local lab infrastructure and independently provisioned test accounts available:

- **First testable one-exit lab integration:** about **5–9 focused engineer-weeks**, as scoped in L1–L6. A deliberately pre-staged single-platform fixture is the shortest path. This is the point at which external monitoring and real clients can exercise the runtime meaningfully.
- **Robust single-exit parity, including full fault/reboot/recovery evidence:** allow **another 2–4 engineer-weeks**, depending on what real Tailscale/netlink/forwarding behavior reveals.
- **Complete five+direct, persistent clients/proxies, native migration/adapters, supported services/platforms and binding acceptance:** roughly **4–8 engineer-months total from this snapshot**, including the above, for an experienced solo owner. This is a low-to-moderate-confidence range, not a source-derived percentage complete. A significant redesign discovered at the first real integration, unavailable native ARM64 execution, or difficult migration/proxy fault behavior can push it beyond that range.

Focused additional engineers could shorten elapsed time on clients, platform support or migration after interfaces stabilize; the owner/activation/security review and fault-proofing critical path will not scale linearly. Runtime debugging, independent review, repeated measured workloads and soak elapsed time must remain in the schedule. Latest offline harness or component PASS counts do not reduce these obligations.

Recommended next implementation unit: **a reviewed, single-platform lab owner plus a typed continuation from `BootstrappedOwner` to quarantined live links and daemon/monitor/expiry custody**. Keep the public launch refusal until that path satisfies its prerequisite gates, then test the real packet path before expanding to fleet or migration work. Release readiness remains **unverified**; this research did not execute or qualify any runtime.
